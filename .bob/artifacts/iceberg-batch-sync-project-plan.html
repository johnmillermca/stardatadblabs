Iceberg Batch Sync — Project Plan

Stardata (Apache Doris) → Polaris Iceberg catalog · Incremental sync via snap_id watermark · Console UI at stardata.stardatadb.com

What we are building

Console feature

  • New Lakehouse sync tab in stardata.stardatadb.com
  • Table showing all synced Iceberg tables + live batch status
  • + Create Iceberg Table button → guided modal
  • Per-table detail panel: KPIs, batch history, Blocked badge
  • Clear error and resume action with confirmation

Batch sync job

  • Reads from cache_system.<table> control rows
  • UPSERT batches: MERGE INTO Iceberg on primary key
  • DELETE batches: reads __DORIS_DELETE_SIGN__=1
  • snap_id window: (from, to] — fixed before read
  • Error isolation: one failure blocks only that table

Key constraints and correctness fixes

#1 — No timestamp-based dedup. Two rows can share the same updated_at. Merge uses the app table's UNIQUE KEY columns (not timestamps). updated_at only decides which version wins in MATCHED.
#2 — Hidden columns filter. With show_hidden_columns=true Doris returns delete-marked rows. Upsert reads filter __DORIS_DELETE_SIGN__=0. Delete reads filter =1.
#3 — Delete window before compaction. Doris removes delete-sign rows during compaction. Delete batches run more frequently than compaction (hourly vs default 4-hour compaction).
#4 — Status written correctly. Status is set to delete_pending before the DELETE runs. Only set to deleted after Iceberg confirms commit. Failed state written on exception.
#5 — Exclusive lower bound. Next window uses snap_id > last_completed_to, never >=. Upper bound captured once at batch start to prevent moving target.
#6 — Fixed upper bound per batch. SELECT max(snap_id) captured before reading rows. All reads in the batch use this fixed to value.
#7 — Duplicate table name. If the same table name exists in more than one app database, the console shows a picker. The job also fails fast and surfaces this in the log.

Data flow

● App table created with PROPERTIES ("stardata.table_type"="iceberg") in Stardata
↓ FE patch injects snap_id, created_at, updated_at, MOW, auto-partition
↓ DDL mirror sidecar creates empty cache_system.<table> tracking shell
● Nothing else happens — table is Stardata only
↓ User opens Lakehouse sync tab, picks table, clicks Create Iceberg Table
↓ Console validates: source resolution → eligibility → columns → type mapping
↓ Console creates: Polaris namespace <db>_iceberg → Iceberg table (v2, identifier fields) → initialises control rows
● Sync job picks up the table on its next run
↓ INITIAL batch: snap_id 0 → max(snap_id), upserts all rows
↓ Incremental UPSERT batches every run: snap_id > last_to AND ≤ new_max, __DORIS_DELETE_SIGN__=0
↓ DELETE batches (same or next run): same window, __DORIS_DELETE_SIGN__=1
● Control rows in cache_system.<table> track every batch
● On failure: writes to cache_system.<table>_log → table is Blocked
↓ Operator clears error from console → next run retries same window (idempotent)

Incremental sync algorithm (per table, per run)

1
Gate check. If cache_system.<table>_log exists and has rows → mark Blocked, stop. Release advisory lock on exit.
2
Fix window. from = max(snap_id_to) WHERE status IN ('completed upsert','deleted'). to = SELECT max(snap_id) FROM <app_db>.<table>. If to ≤ from → nothing new, stop.
3
Record batch. INSERT control row: type=UPSERT (or INITIAL if from=0), snap_id_from, snap_id_to, max(created_at), max(updated_at), status=running.
4
Read changed rows. SET show_hidden_columns=true then SELECT … WHERE snap_id > :from AND snap_id <= :to AND __DORIS_DELETE_SIGN__=0.
5
MERGE INTO Iceberg. On primary key. MATCHED AND s.updated_at >= t.updated_at → UPDATE SET *. NOT MATCHED → INSERT *.
6
Close upsert. On success → status=completed upsert. On failure → status=failed, write log row, stop.
7
Read deletes. del_from = max(snap_id_to) WHERE batch_type='DELETE' AND status='deleted'. Same to. SELECT PK cols WHERE __DORIS_DELETE_SIGN__=1.
8
Apply deletes. Insert DELETE control row with status=delete_pending. DELETE FROM polaris.… WHERE (pk) IN (…). On success → status=deleted. On failure → status=failed, write log row, stop.
9
Repeat. Next run starts at the highest completed snap_id_to. No row is ever read twice.

Console UI screens

Screen 1 — Lakehouse sync tab (list view)

  • Title: Lakehouse tables · subtitle: Iceberg tables via JDBC · Every 6 h · hot tables every 5 min
  • Database filter dropdown (populated from synced tables' app databases)
  • + Create Iceberg Table button (top right)
  • Table: TABLE · DATABASE · FORMAT · LAST UPDATED · SIZE · SYNC STATUS · ACTIONS
  • Status colours: green (completed upsert / deleted), blue (running), orange (delete_pending), red (failed / Blocked)
  • Blocked badge in red pill next to status text
  • Details button per row → opens detail panel below

Screen 2 — Per-table detail panel

  • KPI strip: Last snap_id · Last batch time · Rows upserted · Rows deleted · Status
  • Blocked banner (red) with full error_message from cache_system.<table>_log
  • Clear error and resume → confirmation → truncates log table, re-enables sync
  • Recent batches table: Batch # · Type · snap_id from→to · Rows · max(created_at) · max(updated_at) · Status · Started · Finished

Screen 3 — Create Iceberg Table modal

  • Step 1: Dropdown lists only iceberg-eligible cache_system tables (not already synced, not *_log)
  • DB disambiguation picker if same table name appears in multiple app databases
  • Preview: Source sales.orders → Target polaris.sales_iceberg.orders
  • Column checks: snap_id ✅ · created_at ✅ · updated_at ✅ — red ✗ if missing, Create button disabled
  • Primary key (merge identifier) display
  • Column type mapping table with Doris → Iceberg types; unsupported types flagged red
  • If Iceberg table already exists: amber warning with Reuse existing / Drop and recreate
  • Create and start sync → animated 8-step progress: resolve → eligibility → validate → namespace → schema → CREATE TABLE → init control → INITIAL batch

Out of scope

  • Ad-hoc SQL querying (handled by QuerySpace / SQL console)
  • Schema migration after first create (column adds/drops — open question)
  • Automatic table creation on stardata.table_type=iceberg property (must be triggered manually from console)
  • Multi-table parallelism (each table holds an advisory lock; runs sequentially per table)
